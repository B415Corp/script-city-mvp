# План: Адаптация документации под SimCity-архитектуру (ядро + модули, тики)

## Цель

Сделать документацию согласованной с реальными потребностями **SimCity-клона**: описать архитектуру с **минимальным ядром**, модульным расширением и работой **по тикам**, так чтобы несколько разработчиков могли комфортно работать параллельно. Мультиплеер и сложную серверную часть фиксируем в документации как **следующие фазы**, но в первой версии описываем только **однопользовательскую клиентскую симуляцию**.

## Базовый стек (для документации)

- **Клиент / игра:** TypeScript + Phaser 3 (2D/изометрия, тайловые карты, камера, viewport).
- **Игровая архитектура:** ECS-подход (сущности, компоненты, системы) + событийная шина.
- **UI-слой:** при необходимости — React поверх канваса (меню, HUD), но не как основной носитель игрового состояния.
- **Сборка и разработка:** Vite, ESLint, Prettier, Jest/Vitest.
- **Сервер и мультиплеер:** Node.js + Socket.io + FastAPI + PostgreSQL/Redis — как задел в разделах "Post-MVP" (описываем на уровне концепции, без детализации протоколов).

## 2. Переписать `docs/development/architecture.md`

1. **Описать уровни архитектуры:**

- **Игровое ядро (Core):**
 - Запускает и управляет игровым циклом (тики).
 - Хранит глобальные менеджеры: ECS, шина событий, менеджер модулей.
 - Управляет временем (deltaTime, фиксированный шаг симуляции).
- **Модули симуляции:** Транспорт, Экономика, Население, Здания, Инфраструктура и т.п.
 - Каждый модуль регистрирует свои компоненты и системы в ядре.
 - Нельзя напрямую лезть в чужие внутренности — только через публичный API/события.
- **Слой представления (Renderer):**
 - Phaser-сцены, тайловая карта, слои (земля, дороги, здания, эффекты).
 - Привязан к данным компонентов (позиция, спрайт, состояние).
- **UI-слой:** меню, панели, оверлеи, не влияющие напрямую на симуляцию, а только посылающие команды ядру.

2. **Расширяемость и модульность:**

- Формализовать понятие **модуля**:
 - Своя папка, свой namespace, публичный API (функции, события, типы).
 - Строгие правила импортов: использовать только Public API других модулей/ядра.
- Описать, как добавлять новый модуль без ломки существующих:
 - Регистрация системы в ECS через точку расширения ядра.
 - Подписка на события ядра (например, "построено здание", "изменён налог").
- Для нескольких разработчиков:
 - Каждый работает преимущественно в «своём» модуле.
 - Согласование только по контрактам API и событиям.
 - Ядро меняется реже и через отдельные обсуждения.

3. **Событийная модель (Event Bus):**

## 3. Принцип работы по тикам (описать в `architecture.md` отдельным разделом)

1. Описать общий цикл тика (game loop) для однопользовательского режима:

- **Сбор ввода:** обработка команд игрока, клики/горячие клавиши, действия UI.
- **Фаза симуляции:**
 - Ядро запускает системы ECS в фиксированном порядке (например: население → экономика → транспорт → инфраструктура).
 - Каждая система читает и изменяет только свои компоненты.
 - Внутри тика генерируются события (например, здание достроено, возникла пробка).
- **Фаза синхронизации состояний:** агрегирование результатов (обновление агрегатных показателей, подсчёт статистики).
- **Фаза рендеринга:** обновление спрайтов и тайлов в Phaser на основе изменённых компонентов.

2. Зафиксировать требования:

- **Фиксированный шаг симуляции** (например, 10–20 тиков в секунду), независимо от FPS рендера.
- Возможность пропуска/догонки тиков (при лаге) за счёт мульти-тика симуляции без лишнего рендера.
- Чёткие правила: бизнес-логика только в системах, без побочных эффектов в рендере.

3. Отдельно отметить, как это будет расширено под мультиплеер в будущем:

- Ядро на клиенте остаётся, но авторитетное состояние переезжает на сервер.
- Клиентский тик становится предсказанием/интерполяцией, серверный — источником правды.
