# Процесс разработки — Script City

Документ описывает, как ведётся работа в репозитории: ветки, коммиты, ревью, релиз.
Правила кода — в [code-style.md](code-style.md), контракт с агентами — в [AGENTS.md](../../AGENTS.md).

## 1. Ветки

**`dev_new` — единственная рабочая ветка проекта.** Вся работа идёт в неё напрямую.

| Ветка     | Назначение                | Правило                                        |
| --------- | ------------------------- | ---------------------------------------------- |
| `dev_new` | **единственная рабочая**  | все коммиты напрямую сюда                      |
| `main`    | релизная                  | обновляется только на релизе, через теги       |

Правила:

- Не создаются ветки `feature/*`, `fix/*`, `hotfix/*` и ветки на разработчика.
- Pull request'ы и merge для повседневной работы не используются.
- Одна логическая задача — один коммит в `dev_new`.
- Перед коммитом — `npm run type-check`, `npm run lint`, `npm run test:run`.
- Крупная правка делится на логические коммиты, а не на ветки.

Ранее в проекте использовалось много параллельных веток (`dev`, `refa`, `ecs_manager`,
`ui_kit`, `update_debug` и т.п.) — они удалены из `origin`, их содержимое влито в `dev_new`.
Возврат к этой схеме не приветствуется.

## 2. Коммиты

Conventional Commits — история проекта уже этому следует:

```
<type>(<scope>): <описание в импераливе, до 72 символов>
```

| Тип        | Когда                                       |
| ---------- | ------------------------------------------- |
| `feat`     | новая функциональность                      |
| `fix`      | исправление бага                            |
| `refactor` | изменение структуры без изменения поведения |
| `perf`     | оптимизация с сохранением поведения         |
| `test`     | тесты                                       |
| `docs`     | документация                                |
| `chore`    | зависимости, конфиги, скрипты               |
| `build`    | система сборки                              |
| `ci`       | пайплайны                                   |

Scope — область кода: `ecs`, `core`, `map`, `ui`, `tick`, `tools`, `workflow`, `docs`.

Правила:

- Один коммит — одно логическое изменение. Не миксуй рефакторинг с фичей.
- Тело коммита — **зачем**, а не что: объясни причину, а не перечисление файлов.
- Breaking changes — `!` после scope и блок `BREAKING CHANGE:` в теле.

## 3. Ревью изменений

Отдельных веток и pull request'ов нет, поэтому ревью выполняется **до коммита в `dev_new`**.

Что проверяется:

1. Архитектурные инварианты соблюдены (см. `AGENTS.md`, раздел 5) — логика не знает
   про Phaser, состояние в ECS, общение через `EventBus`.
2. Изменение логически цельное и не содержит попутного рефакторинга.
3. Для новой логики есть тесты.
4. Пройдены `npm run type-check`, `npm run lint`, `npm run test:run`.
5. Есть запись в `CHANGELOG.md` под `[Unreleased]`.
6. Обновлена документация, если изменились архитектура, команды или правила.

Стиль отдельно не ревьюится — его обеспечивает Prettier и ESLint.

## 4. Цикл разработки задачи

```
постановка → воспроизведение → тест → реализация → рефакторинг → проверка → коммит в dev_new
```

- **Воспроизведение** обязательно: агент должен увидеть проблему до правки.
- **Тест до фикса** для багов: красный тест доказывает, что он что-то ловит.
- **Рефакторинг** — отдельный коммит, только после зелёного теста.
- Мелкий дубж-фикс в том же коммите — ок. Попутный рефакторинг чужих модулей — нет,
  это отдельная задача.

## 5. Версии и CHANGELOG

Формат — [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/), версии — SemVer.

```
## [Unreleased]        — накопленные изменения, ещё не released
## [0.1.0] - 2026-01-12 — выбранный релиз
```

- `MAJOR` (X.0.0) — несовместимые изменения ядра или формата данных.
- `MINOR` (0.Y.0) — новая функциональность (новый модуль, новая система, новый инструмент).
- `PATCH` (0.Y.Z) — баги и рефакторинг без новой функциональности.

Что попадает в CHANGELOG: пользовательски значимые изменения, изменения архитектуры
и производительности, важные багфиксы. Не попадает: правки комментариев, форматирование,
переименования приватных полей.

## 6. Релиз

1. Обновить `## [X.Y.Z] - <дата>` в `CHANGELOG.md`.
2. Прогнать полный `npm run build` — он должен быть зелёным.
3. Обновить версию в `package.json`.
4. Тег: `v0.1.0`, аннотированный.
5. Merge `dev_new` → `main`.

## 7. Работа с ИИ-агентами

- Агент читает `AGENTS.md` до правок.
- Агент работает и коммитит **только** в `dev_new`; другие ветки не создаёт.
- Агент не коммитит без явного указания пользователя.
- Агент фиксирует в отчёте: что сделано, чем проверено, что осталось сломанным.
- Агент не добавляет зависимости и не меняет конфиги без согласования.
- Результат работы агента проходит те же Definition of Done и ревью, что и человеческая.

## 8. Технический долг

Долг не «потом». Вносится в `CHANGELOG.md` под `[Unreleased]` или в раздел
«Известные проблемы» в `AGENTS.md`, если он блокирует работу. Задача с оценкой
долга должна быть создана в трекере, а не храниться в голове.
