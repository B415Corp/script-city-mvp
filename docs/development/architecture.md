# Архитектура и расширяемость

Последнее обновление: 2025-11-23

Документ описывает целевую архитектуру проекта Script City как SimCity-подобной игры с упором на:

- минимальное **ядро** (Core), управляющее временем и тиками,
- **модульную симуляцию** (транспорт, экономика, население, здания и т.п.),
- независимый **рендерер на PixiJS**,
- возможность масштабирования до мультиплеера в следующих версиях.

## Обзор архитектуры

Высокоуровневая схема:

- **Игровое ядро (Core)**:
  - центральная точка запуска и координации;
  - цикл тиков (game loop);
  - менеджеры ECS, событий, модулей.
- **Модули симуляции**:
  - транспорт, экономика, население, здания, инфраструктура, политики и др.;
  - каждый модуль регистрирует свои компоненты и системы в ядре.
- **Слой представления (Renderer)**:
  - PixiJS-сцены, спрайты, тайловая карта, эффекты;
  - работает поверх данных компонентов (позиция, состояние).
- **UI-слой**:
  - меню, панели, HUD без React;
  - взаимодействует с ядром через команды и агрегированные данные.
- **Инфраструктурные сервисы поверх PixiJS**:
  - изометрическая математика;
  - менеджер чанков карты;
  - рендерер тайлов и объектов;
  - модель `GameWorld`;
  - задел под слой синхронизации с сервером.

---

## Игровое ядро (Core)

Ядро — это минимальный, но жёстко определённый центр игры.

Основные обязанности:

- **Управление временем и тиками**:
  - фиксированный шаг симуляции (например, 10–20 тиков/сек);
  - учёт реального времени, компенсация лагов (несколько тиков за кадр).
- **Запуск и оркестрация систем ECS**:
  - хранит реестр систем;
  - определяет порядок выполнения (например: население → экономика → транспорт → инфраструктура).
- **Хранение глобальных менеджеров**:
  - ECS (entities, components, systems);
  - Event Bus (событийная шина);
  - менеджер модулей (регистрация и инициализация модулей).
- **Работа в разных режимах**:
  - однопользовательский локальный режим (всё в браузере);
  - в будущем — клиент, синхронизирующийся с сервером (мультиплеер).

Ядро не знает ничего о конкретных деталях UI и не зависит от PixiJS напрямую: оно оперирует абстрактными системами и компонентами.

---

## Модули симуляции

Каждая крупная подсистема игры оформляется как **модуль**.

Примеры модулей:

- **Модуль "Здания"**:
  - хранит типы зданий, уровни, состояния строительства;
  - отвечает за постройку/снос и события строительства.
- **Модуль "Экономика"**:
  - бюджет города, налоги, расходы;
  - агрегирование доходов от зданий и населения.
- **Модуль "Население"**:
  - группы населения, спрос на жильё и работу;
  - миграция, благополучие.
- **Модуль "Транспорт"**:
  - дорожная сеть, пробки, общественный транспорт;
  - маршрутизация.
- **Модуль "Инфраструктура"**:
  - электричество, вода, отходы, связь.
- **Модуль "Политики и законы"**:
  - влияющие на другие модули параметры (налоги, ограничения, бонусы).

### Формализация модуля

Модуль:

- имеет **свою папку**, namespace и публичный API:
  - функции (например, `registerTransportModule(core)`),
  - события (типы событий, которые он генерирует или слушает),
  - типы данных (компоненты, конфиги).
- **не имеет права** напрямую лезть во внутренности других модулей:
  - любые связи — через:
    - публичные функции/интерфейсы,
    - события в Event Bus,
    - общие компоненты/данные, определённые в ядре или `shared`-слое.

Добавление нового модуля:

1. Описать публичный API и события.
2. Зарегистрировать его системы в ядре через точку расширения (например, `core.registerSystem()`).
3. Подписаться на нужные события других модулей через Event Bus.

## Слой представления (Renderer)

Renderer отвечает только за визуализацию текущего состояния мира.

Основные элементы:

- **PixiJS-сцена**:
  - основной канвас;
  - один или несколько слоёв: фон, тайлы, дороги, здания, эффекты, UI.
- **Тайловая карта**:
  - карта делится на чанки;
  - каждый чанк знает свои спрайты и их состояние.
- **Связь с ECS**:
  - компоненты содержат данные о позиции, типе спрайта, состоянии (строится/готово/разрушено);
  - Renderer читает эти компоненты и создаёт/обновляет/удаляет спрайты.

Ключевой принцип: **никакой игровой логики в Renderer**. Он только "рисует" результат работы систем симуляции.

---

## UI-слой

UI-слой строится без React и представляет собой:

- **HUD и панели**:
  - информация о бюджете, населении, политике;
  - кнопки режимов, скорости времени, выбора инструментов.
- **Окна и диалоги**:
  - свойства зданий;
  - лог событий;
  - настройки.

Правила:

- UI не хранит `GameState`.
- Любое действие игрока = отправка **команды** ядру (например, `BuildBuilding`, `Bulldoze`, `ChangeTax`).
- UI подписывается на **агрегированные данные** и события (например, текущий бюджет, статусы модулей), а не на сырые структуры ECS.

---

## Событийная модель (Event Bus)

Event Bus позволяет модулям и слоям обмениваться информацией без жёстких связей.

Типы событий:

- **Игровые**:
  - `ConstructionStarted`, `ConstructionCompleted`;
  - `TrafficJamStarted`, `TrafficJamResolved`;
  - `PolicyApplied`, `PolicyRevoked`.
- **Системные**:
  - `TickStarted`, `TickEnded`;
  - смена игрового режима (пауза, нормальная скорость, ускорение).
- **UI-команды** (как отдельный поток или тип событий):
  - `BuildCommandRequested`;
  - `DemolishCommandRequested`;
  - `ChangeTaxRequested`.

Использование:

- системы внутри модулей:
  - публикуют события о своих изменениях;
  - подписываются только на те события, которые им нужны;
- UI:
  - публикует команды;
  - подписывается на агрегированные события (для обновления панелей).

## Инфраструктурные сервисы поверх PixiJS

Эти сервисы обеспечивают основу для работы с картой и рендером.

### `IsometricMath`

Назначение:

- конвертация координат **тайлов** в экранные координаты и обратно:
  - `tileToScreen(tileX, tileY) → { x, y }`;
  - `screenToTile(screenX, screenY) → { tileX, tileY }`.
- учёт:
  - размеров тайла;
  - смещений камеры;
  - изометрической проекции.

### `ChunkManager`

Назначение:

- деление карты на **чанки** (например, 64×64 тайлов);
- определение, какие чанки сейчас находятся в зоне видимости камеры;
- загрузка/выгрузка чанков:
  - и на уровне данных (`GameWorld`),
  - и на уровне рендера (спрайты в PixiJS).

### `TileRenderer`

Назначение:

- создание спрайтов для тайлов и объектов;
- обновление спрайтов при изменении компонентов (тип, состояние, текстуры);
- удаление спрайтов, когда чанки выгружаются или объекты исчезают.

### `GameWorld`

Назначение:

- модель состояния мира, независимая от UI и транспорта:
  - тайлы и их параметры;
  - здания, дороги, объекты;
  - связи с компонентами ECS.
- требования:
  - сериализуемость (для сохранений и передачи на сервер);
  - возможность частичной загрузки (по чанкам).

### Слой синхронизации

В будущем:

- абстракция, через которую ядро и `GameWorld` могут:
  - работать **локально** (один процесс, без сети);
  - или через **сервер** (WebSocket, Socket.io).
- интерфейс не зависит от конкретного транспорта:
  - команды (`Command`) и снапшоты/патчи состояния.

## Принцип работы по тикам

Подробное описание тиков вынесено в отдельный документ `tick-and-simulation.md`. Здесь — только обзор.

### Общий цикл тика (однопользовательский режим)

1. **Сбор ввода**:
   - обработка кликов, горячих клавиш, действий UI;
   - формирование списка команд (`Command[]`).
2. **Фаза симуляции**:
   - ядро последовательно запускает системы в определённом порядке (например: население → экономика → транспорт → инфраструктура);
   - каждая система:
     - читает только нужные компоненты;
     - модифицирует только свои данные;
   - генерируются события в Event Bus.
3. **Фаза синхронизации состояний**:
   - обновление агрегатов (бюджет, статистика населения, сводки по транспорту);
   - подготовка данных для UI.
4. **Фаза рендеринга**:
   - Renderer (PixiJS) обновляет/создаёт/удаляет спрайты на основе изменённых компонентов.

### Требования к тикам

- фиксированный шаг симуляции (например, 100 мс = 10 тиков/сек);
- возможность:
  - паузы;
  - ускорения (например, 3×, 5× за счёт ускоренного проигрывания тиков);
  - догонки (несколько тиков подряд без промежуточного рендера при лаге).
- бизнес-логика:
  - только в системах;
  - рендер не должен менять игровое состояние.

### Путь к мультиплееру

В будущем:

- клиентское ядро остаётся тем же;
- авторитетное состояние `GameWorld` переезжает на сервер;
- клиент:
  - отправляет команды;
  - получает снапшоты/патчи и привязывает к своему уже знакомому формату;
  - использует локальные тики как предсказание/интерполяцию.

## Минимальное ядро (MVP) и модульные расширения

### Минимальное ядро (MVP)

Состав:

- управление временем и тиками;
- базовая ECS:
  - реестр сущностей (Entity registry);
  - хранилище компонентов (Components store);
  - раннер систем (Systems runner);
- базовый набор компонентов:
  - позиция;
  - визуальное представление;
  - параметры базовых зданий;
- карта:
  - простое тайловое поле (сразу с поддержкой чанков);
  - базовый рендер на PixiJS.

### Минимальные модули для старта

1. **Модуль "Здания"**:
   - базовые типы зданий (жилые/коммерческие/промышленные);
   - логика постройки и сноса;
   - события: начало/завершение строительства.
2. **Модуль "Экономика (упрощённая)"**:
   - доходы/расходы города;
   - привязка к зданиям (налоги, обслуживание).
3. **Модуль "Городская карта"**:
   - управление чанками;
   - связь с `ChunkManager` и `TileRenderer`;
   - загрузка/выгрузка данных по мере движения камеры.

Дальнейшие модули (население, транспорт, инфраструктура, политики) добавляются **поверх** этого ядра без его переписывания.

## Совместная разработка

### Ответственность модулей и ядра

- Ядро и инфраструктурные сервисы:
  - меняются редко;
  - изменения проходят отдельное обсуждение/ревью.
- Модули:
  - могут развиваться параллельно разными разработчиками;
  - обязаны строго следовать контрактам API и событий.

### Рекомендации по процессу

- Новая подсистема:
  - сначала короткое описание в `development/` (мини-RFC);
  - затем реализация модуля через публичный API и события.
- Правила:
  - запрет на прямой доступ к внутренним структурам чужих модулей;
  - запрет на хранение игрового состояния в UI;
  - использование общих компонентов и событий для интеграции.

### Пример распределения ответственности

- **Разработчик A — модуль "Здания"**:
  - типы зданий, уровни, состояния строительства;
  - логика постройки и сноса;
  - события строительства.
- **Разработчик B — модуль "Экономика"**:
  - бюджет города, налоги, расходы;
  - агрегирование доходов;
  - события изменения экономических параметров.
- **Разработчик C — модуль "Транспорт"**:
  - дорожная сеть, маршрутизация;
  - управление трафиком;
  - события пробок и ДТП.

Общее взаимодействие только через события Event Bus и публичные API модулей.

## Принципы расширяемости и паттерны проектирования

### Plugin-based подход

1. **Регистрация модулей**: централизованный реестр для регистрации новых компонентов в ядре.
2. **Хуки жизненного цикла**: точки входа для расширения функциональности (инициализация, обновление, завершение).
3. **Event-driven архитектура**: подписка на события системы через Event Bus.
4. **Dependency Injection**: внедрение зависимостей для гибкой конфигурации модулей.

### Конфигурируемость

- JSON/YAML конфиги для параметров симуляции.
- Настройка баланса через внешние файлы.
- Профили сложности и режимов игры.
- Переопределение дефолтных значений без изменения кода.

### Версионирование

- Семантическое версионирование API модулей.
- Обратная совместимость схем данных.
- Миграции при изменении структур сохранений.
- Документирование breaking changes.

### Паттерны проектирования

#### Entity-Component-System (ECS)

Для игровых объектов (здания, транспорт, агенты):

- **Entity**: уникальный идентификатор сущности.
- **Component**: данные (позиция, состояние, параметры).
- **System**: логика обработки компонентов.

Преимущества:

- гибкая композиция объектов;
- производительность за счет кэш-локальности;
- лёгкая сериализация состояния;
- простота тестирования систем.

#### Observer/PubSub (Event Bus)

Для событийной модели:

- события симуляции (ДТП, банкротства, достижения);
- обновления UI;
- межмодульная коммуникация;
- логирование и аналитика.

#### Strategy Pattern

Для алгоритмов:

- маршрутизация (разные алгоритмы);
- ценообразование (модели рынка);
- поведение агентов (настройки реализма).

#### Factory Pattern

Для создания объектов:

- здания разных типов;
- транспортные средства;
- политики и законы;
- инфраструктурные объекты.

### Технические требования к модулям и расширениям

1. **TypeScript strict mode**: строгая типизация для всего кода.
2. **ESLint правила**: единый стиль кода, обязательные проверки.
3. **Unit тесты**: покрытие критичной логики систем.
4. **Документация**: JSDoc для публичных API модулей.
5. **Производительность**: профилирование, оптимизация узких мест.

### Границы модулей

#### Запрещено:

- прямой импорт из внутренних папок других модулей;
- циклические зависимости между модулями;
- глобальное состояние вне ядра (ECS/Event Bus);
- мутация данных напрямую, минуя системы.

#### Рекомендуется:

- использование Public API модулей;
- иммутабельность данных (там, где возможно);
- чистые функции для бизнес-логики;
- типизированные события и команды.

### Масштабирование производительности

#### Оптимизации:

1. **Чанкинг карты**: деление на чанки, загрузка/выгрузка по требованию.
2. **Viewport culling**: рендер только видимых объектов.
3. **Web Workers**: вынос тяжёлых расчётов в фоновые потоки (например, маршрутизация).
4. **Аггрегация**: групповое моделирование агентов (вместо симуляции каждого отдельно).
5. **LOD (Level of Detail)**: детализация в зависимости от зума и расстояния.
6. **Инкрементальные обновления**: пересчёт только изменённых участков.
7. **Spatial indexing**: эффективный поиск объектов по координатам (сетки, квадродеревья).

#### Настройки производительности:

- частота тиков симуляции (настраиваемая);
- глубина расчётов (упрощённая/реалистичная);
- лимиты количества агентов;
- детализация графиков и маршрутов.
