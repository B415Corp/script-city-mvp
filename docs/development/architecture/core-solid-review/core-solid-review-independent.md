# Независимая SOLID-оценка ядра

**Теги**: `arch:core`, `quality:solid`, `quality:cleancode`, `arch:ecs`, `arch:events`, `arch:commands`, `review:independent`

## Контекст и методика

Оценка выполнена по общим принципам SOLID и чистого кода из `development/architecture/solid-oop.md`, без опоры на продуктовые/дорожные цели из `core.md` и соседних документов. Рассматривались публичные API и ответственность слоёв в `src/core`.

## Сильные стороны

- Есть явные координаторы (`TickManager`, `CommandProcessor`, `ModuleManager`, `MapManager`), что создаёт основу для разделения ответственности.
- Командная шина и EventBus уже отделены от систем ECS, что упрощает точечные refactors.
- Конфигурация модулей и карт вынесена в менеджеры, что облегчает инъекцию зависимостей при дальнейшей декомпозиции.

## Основные нарушения SOLID (по влиянию на поддерживаемость)

- **SRP/ISP в TickManager**: сочетает управление временем, обработку команд и запуск систем. Это смешивает домены и вынуждает потребителей зависеть от всего набора обязанностей.
- **OCP в CommandProcessor**: централизованный `switch` по типам команд. Новые команды требуют изменения общего класса вместо расширения через хэндлеры.
- **SRP/DIP в MapManager**: объединены загрузка данных, рендер, ввод и подсветка; напрямую зависит от `Phaser.Scene` и `GameCore`, что ограничивает повторное использование в headless/тестовых сценариях.
- **SRP в ModuleManager**: внутрь менеджера просачивается UI-слой (Phaser), ломая границу между симуляцией и представлением.
- **DIP в SaveManager**: работает с конкретными структурами ECS/модулей через `JSON.stringify`, без контракта снапшотов и версионирования.
- **SRP в EventBus**: транспорт смешан с диагностикой (хранение истории, самоподписка на тики), что затрудняет лёгкую подмену шины.

## Риски для качества кода

- **Тестируемость**: жёсткие зависимости на Phaser и конкретные менеджеры усложняют unit-тесты без движка.
- **Расширяемость**: централизованные `switch` и отсутствие реестров хэндлеров ведут к росту цикломатической сложности при добавлении команд/модулей.
- **Поддержка версий**: отсутствие контрактов снапшотов может привести к хрупким сохранениям и невозможности миграций.
- **Наблюдаемость**: диагностика встроена в EventBus, что увеличивает шум в проде и затрудняет выборочное включение телеметрии.

## Быстрые исправления (минимум затраты → максимум эффекта)

1. Вынести из `TickManager` вызовы команд и систем в отдельный `SimulationLoop`, оставив в менеджере только тайминг и события тиков.
2. Ввести `CommandRegistry` с хэндлерами, регистрируемыми модулями; `CommandProcessor` ищет хэндлеры по типу вместо `switch`.
3. Разделить `MapManager` на `IMapService` (core, данные/ивенты) и рендерный адаптер для Phaser на уровне сцен.
4. Удалить Phaser-зависимости из `ModuleManager`; сцены сами вызывают `attachToScene` у модулей, если он есть.
5. Описать `ISnapshotProvider<T>` для ECS/модулей и заставить `SaveManager` работать только через эти интерфейсы с версионированием.
6. Сделать EventBus без истории по умолчанию, а телеметрию вынести в декоратор `DevEventBus`.

## Наблюдения по чистому коду

- Сильная связность между менеджерами и конкретными реализациями осложняет замену подсистем (например, headless симуляция или другой рендерер).
- Командный слой не изолирует валидацию от применения; стоит разделить `validate`/`apply` и контекст исполнения.
- Публичные API менеджеров не всегда минимальны: стоит экспонировать только операции на своём домене, пряча детали сцен/рендера.
