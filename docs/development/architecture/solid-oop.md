# SOLID и ООП принципы

Документ описывает применение принципов SOLID и объектно-ориентированного программирования в архитектуре Script City.

## SOLID принципы

### S — Single Responsibility Principle (Принцип единственной ответственности)

Каждый класс, модуль или система должны иметь только одну причину для изменения.

#### В ядре (Core)

- **`TickManager`** — отвечает только за управление временем и тиками:
  - не знает о системах ECS;
  - не управляет событиями напрямую;
  - не обрабатывает команды.
- **`ECSManager`** — управляет только ECS (entities, components, systems):
  - не знает о времени;
  - не обрабатывает события (только получает их через параметры);
  - не управляет модулями.
- **`EventBus`** — только публикация и подписка на события:
  - не знает о содержимом событий;
  - не валидирует события;
  - не обрабатывает бизнес-логику.
- **`ModuleManager`** — только регистрация и инициализация модулей:
  - не знает о содержимом модулей;
  - не управляет зависимостями модулей напрямую (только порядок инициализации).
- **`CommandProcessor`** — только обработка команд:
  - не знает о UI;
  - не знает о конкретных системах (валидирует и передаёт дальше).

#### В модулях

- **Модуль "Здания"**:
  - отвечает только за здания (создание, удаление, состояние);
  - не управляет экономикой напрямую (публикует события);
  - не управляет населением напрямую.
- **Модуль "Экономика"**:
  - отвечает только за бюджет, налоги, расходы;
  - не управляет зданиями напрямую (слушает события);
  - не управляет населением напрямую.
- **Модуль "Транспорт"**:
  - отвечает только за дорожную сеть, пробки, маршрутизацию;
  - не управляет зданиями напрямую;
  - не управляет экономикой напрямую.

#### Пример нарушения

```typescript
// ❌ Плохо: TickManager делает слишком много
class TickManager {
  tick() {
    // управление временем
    this.currentTick++;
    // обработка систем (не его ответственность!)
    this.ecsManager.runSystems();
    // публикация событий (не его ответственность!)
    this.eventBus.emit('TickEnded');
  }
}

// ✅ Хорошо: TickManager только управляет временем
class TickManager {
  tick() {
    this.currentTick++;
    // публикует событие, но не обрабатывает его
    this.eventBus.emit('TickStarted', { tick: this.currentTick });
  }
}
```

### O — Open/Closed Principle (Принцип открытости/закрытости)

Программные сущности должны быть открыты для расширения, но закрыты для модификации.

#### В ядре

- **`GameCore`** — закрыт для модификации, открыт для расширения:
  - нельзя изменять внутреннюю логику ядра для добавления новых модулей;
  - можно регистрировать новые модули через `ModuleManager`;
  - можно регистрировать новые системы через `ECSManager`.
- **`EventBus`** — закрыт для модификации, открыт для расширения:
  - нельзя изменять логику публикации/подписки;
  - можно добавлять новые типы событий без изменения кода EventBus.
- **`CommandProcessor`** — закрыт для модификации, открыт для расширения:
  - нельзя изменять логику обработки команд;
  - можно добавлять новые типы команд через интерфейс `ICommand`.

#### В модулях

- **Системы ECS** — закрыты для модификации, открыты для расширения:
  - нельзя изменять базовую логику системы;
  - можно добавлять новые системы через интерфейс `ISystem`;
  - можно расширять функциональность через композицию компонентов.
- **Модули** — закрыты для модификации, открыты для расширения:
  - нельзя изменять код модуля для добавления новой функциональности;
  - можно создавать новые модули через интерфейс `IModule`;
  - можно расширять через события и подписки.

#### Пример

```typescript
// ✅ Хорошо: можно добавить новую систему без изменения ECSManager
class PopulationSystem implements ISystem {
  id = 'population';
  priority = 1;
  updateInterval = 1;
  
  update(deltaTime: number, ecs: ECSManager, eventBus: EventBus) {
    // логика системы
  }
}

// Регистрация без изменения кода ECSManager
ecsManager.registerSystem(new PopulationSystem());

// ✅ Хорошо: можно добавить новую команду без изменения CommandProcessor
class BuildBuildingCommand implements ICommand {
  type = 'BuildBuilding';
  timestamp = Date.now();
  position: { x: number; y: number };
  buildingType: string;
  
  validate() {
    // валидация команды
  }
}

// Обработка без изменения кода CommandProcessor
commandProcessor.enqueueCommand(new BuildBuildingCommand());
```

### L — Liskov Substitution Principle (Принцип подстановки Лисков)

Объекты в программе должны быть заменяемыми на экземпляры их подтипов без изменения правильности программы.

#### В ядре

- **`ISystem`** — все системы должны быть взаимозаменяемы:
  - любая система, реализующая `ISystem`, должна работать с `ECSManager`;
  - нельзя требовать от системы специфичных методов, не описанных в интерфейсе.
- **`IModule`** — все модули должны быть взаимозаменяемы:
  - любой модуль, реализующий `IModule`, должен работать с `ModuleManager`;
  - нельзя требовать от модуля специфичных методов, не описанных в интерфейсе.
- **`ICommand`** — все команды должны быть взаимозаменяемы:
  - любая команда, реализующая `ICommand`, должна работать с `CommandProcessor`;
  - нельзя требовать от команды специфичных методов, не описанных в интерфейсе.

#### В модулях

- **Компоненты ECS** — все компоненты должны быть взаимозаменяемы:
  - любой компонент должен работать с `ECSManager`;
  - нельзя требовать от компонента специфичных методов.
- **Системы модулей** — все системы должны быть взаимозаменяемы:
  - любая система модуля должна работать с `ECSManager`;
  - нельзя требовать от системы специфичных методов, не описанных в `ISystem`.

#### Пример нарушения

```typescript
// ❌ Плохо: система требует специфичный метод, не описанный в ISystem
class SpecialSystem implements ISystem {
  id = 'special';
  priority = 1;
  updateInterval = 1;
  
  update(deltaTime: number, ecs: ECSManager, eventBus: EventBus) {
    // требует специальный метод, которого нет в других системах
    this.specialMethod(); // ❌ нарушение LSP
  }
  
  specialMethod() {
    // специфичная логика
  }
}

// ✅ Хорошо: система использует только методы из интерфейса
class SpecialSystem implements ISystem {
  id = 'special';
  priority = 1;
  updateInterval = 1;
  
  update(deltaTime: number, ecs: ECSManager, eventBus: EventBus) {
    // использует только стандартные методы из интерфейсов
    const entities = ecs.getAllEntities();
    // логика системы
  }
}
```

### I — Interface Segregation Principle (Принцип разделения интерфейсов)

Клиенты не должны зависеть от интерфейсов, которые они не используют.

#### В ядре

- **`ISystem`** — минимальный интерфейс для систем:
  - содержит только необходимые методы (`id`, `priority`, `updateInterval`, `update`);
  - не содержит методов, которые нужны не всем системам.
- **`IModule`** — минимальный интерфейс для модулей:
  - содержит только необходимые методы (`id`, `dependencies`, `initialize`, `destroy`);
  - опциональные методы (`registerSystems`) вынесены отдельно.
- **`ICommand`** — минимальный интерфейс для команд:
  - содержит только необходимые методы (`type`, `timestamp`);
  - опциональные методы (`validate`) вынесены отдельно.

#### В модулях

- **Компоненты** — минимальные интерфейсы:
  - компонент содержит только необходимые данные;
  - не содержит методов, которые нужны не всем компонентам.
- **Системы модулей** — минимальные интерфейсы:
  - система использует только необходимые методы из `ECSManager`;
  - не требует методов, которые нужны не всем системам.

#### Пример

```typescript
// ❌ Плохо: интерфейс содержит методы, которые нужны не всем системам
interface ISystem {
  id: string;
  priority: number;
  updateInterval: number;
  update(deltaTime: number, ecs: ECSManager, eventBus: EventBus): void;
  render?(context: CanvasRenderingContext2D): void; // ❌ нужен не всем
  serialize?(): string; // ❌ нужен не всем
}

// ✅ Хорошо: минимальный интерфейс, опциональные методы вынесены отдельно
interface ISystem {
  id: string;
  priority: number;
  updateInterval: number;
  update(deltaTime: number, ecs: ECSManager, eventBus: EventBus): void;
}

interface IRenderableSystem extends ISystem {
  render(context: CanvasRenderingContext2D): void;
}

interface ISerializableSystem extends ISystem {
  serialize(): string;
}
```

### D — Dependency Inversion Principle (Принцип инверсии зависимостей)

Модули высокого уровня не должны зависеть от модулей низкого уровня. Оба должны зависеть от абстракций.

#### В ядре

- **`GameCore`** — зависит от абстракций:
  - зависит от интерфейсов (`ISystem`, `IModule`, `ICommand`);
  - не зависит от конкретных реализаций систем, модулей, команд.
- **`ECSManager`** — зависит от абстракций:
  - зависит от интерфейса `ISystem`;
  - не зависит от конкретных реализаций систем.
- **`ModuleManager`** — зависит от абстракций:
  - зависит от интерфейса `IModule`;
  - не зависит от конкретных реализаций модулей.
- **`CommandProcessor`** — зависит от абстракций:
  - зависит от интерфейса `ICommand`;
  - не зависит от конкретных реализаций команд.

#### В модулях

- **Системы модулей** — зависят от абстракций:
  - зависят от интерфейсов (`ECSManager`, `EventBus`);
  - не зависят от конкретных реализаций менеджеров.
- **Модули** — зависят от абстракций:
  - зависят от интерфейса `GameCore`;
  - не зависят от конкретной реализации ядра.

#### Пример

```typescript
// ✅ Хорошо: система зависит от абстракций
class PopulationSystem implements ISystem {
  id = 'population';
  priority = 1;
  updateInterval = 1;
  
  update(deltaTime: number, ecs: ECSManager, eventBus: EventBus) {
    // использует только методы из интерфейсов
    const entities = ecs.getAllEntities();
    eventBus.emit('PopulationUpdated', { count: entities.length });
  }
}

// ❌ Плохо: система зависит от конкретной реализации
class PopulationSystem implements ISystem {
  id = 'population';
  priority = 1;
  updateInterval = 1;
  
  update(deltaTime: number, ecs: ConcreteECSManager, eventBus: ConcreteEventBus) {
    // зависит от конкретных классов, а не интерфейсов
    ecs.specificMethod(); // ❌ нарушение DIP
  }
}
```

## ООП принципы

### Инкапсуляция

Скрытие внутренней реализации и предоставление публичного API.

#### В ядре

- **`GameCore`** — инкапсулирует внутренние менеджеры:
  - внутренние менеджеры (`TickManager`, `ECSManager`, `EventBus`) не доступны напрямую;
  - доступ через публичные методы (`getTickManager()`, `getECSManager()`, `getEventBus()`).
- **`TickManager`** — инкапсулирует внутреннее состояние:
  - внутренние переменные (`currentTick`, `gameTime`, `realTime`) не доступны напрямую;
  - доступ через публичные методы (`getCurrentTick()`, `getGameTime()`, `getRealTime()`).
- **`ECSManager`** — инкапсулирует внутреннее хранилище:
  - внутренние структуры данных (entities, components, systems) не доступны напрямую;
  - доступ через публичные методы (`createEntity()`, `addComponent()`, `registerSystem()`).

#### В модулях

- **Модули** — инкапсулируют внутреннюю логику:
  - внутренние системы и компоненты не доступны напрямую;
  - доступ через публичный API модуля (функции, события, типы данных).
- **Системы** — инкапсулируют внутреннюю логику:
  - внутренние переменные и методы не доступны напрямую;
  - доступ через интерфейс `ISystem`.

#### Пример

```typescript
// ✅ Хорошо: инкапсуляция внутреннего состояния
class TickManager {
  private currentTick: number = 0;
  private gameTime: number = 0;
  private realTime: number = 0;
  
  getCurrentTick(): number {
    return this.currentTick;
  }
  
  getGameTime(): number {
    return this.gameTime;
  }
  
  private tick() {
    this.currentTick++;
    this.gameTime += this.tickDuration;
    this.realTime = Date.now();
  }
}

// ❌ Плохо: отсутствие инкапсуляции
class TickManager {
  public currentTick: number = 0; // ❌ публичное поле
  public gameTime: number = 0; // ❌ публичное поле
  
  tick() {
    this.currentTick++;
    this.gameTime += this.tickDuration;
  }
}
```

### Наследование

Использование наследования для переиспользования кода и создания иерархий классов.

#### В ядре

- **Базовые классы менеджеров** — минимальное использование наследования:
  - предпочтение композиции над наследованием;
  - использование интерфейсов вместо абстрактных классов.
- **Исключения** — наследование используется для:
  - базовых классов событий (если нужна общая функциональность);
  - базовых классов команд (если нужна общая функциональность).

#### В модулях

- **Системы модулей** — не используют наследование:
  - все системы реализуют интерфейс `ISystem`;
  - предпочтение композиции над наследованием.
- **Компоненты** — не используют наследование:
  - компоненты — это простые структуры данных;
  - предпочтение композиции над наследованием.

#### Пример

```typescript
// ✅ Хорошо: использование интерфейсов вместо наследования
interface ISystem {
  id: string;
  priority: number;
  updateInterval: number;
  update(deltaTime: number, ecs: ECSManager, eventBus: EventBus): void;
}

class PopulationSystem implements ISystem {
  // реализация интерфейса
}

class EconomySystem implements ISystem {
  // реализация интерфейса
}

// ❌ Плохо: использование наследования для систем
abstract class BaseSystem {
  abstract update(deltaTime: number, ecs: ECSManager, eventBus: EventBus): void;
}

class PopulationSystem extends BaseSystem {
  // наследование от базового класса
}
```

### Полиморфизм

Использование полиморфизма для работы с разными типами через единый интерфейс.

#### В ядре

- **`ECSManager`** — полиморфизм через интерфейс `ISystem`:
  - все системы обрабатываются одинаково через `ISystem`;
  - разные системы могут иметь разную реализацию `update()`.
- **`ModuleManager`** — полиморфизм через интерфейс `IModule`:
  - все модули обрабатываются одинаково через `IModule`;
  - разные модули могут иметь разную реализацию `initialize()`.
- **`CommandProcessor`** — полиморфизм через интерфейс `ICommand`:
  - все команды обрабатываются одинаково через `ICommand`;
  - разные команды могут иметь разную реализацию `validate()`.

#### В модулях

- **Системы модулей** — полиморфизм через интерфейс `ISystem`:
  - все системы обрабатываются одинаково через `ISystem`;
  - разные системы могут иметь разную реализацию `update()`.
- **Компоненты** — полиморфизм через тип `ComponentType`:
  - все компоненты обрабатываются одинаково через `ComponentType`;
  - разные компоненты могут иметь разную структуру данных.

#### Пример

```typescript
// ✅ Хорошо: полиморфизм через интерфейс
class ECSManager {
  private systems: ISystem[] = [];
  
  registerSystem(system: ISystem) {
    this.systems.push(system);
  }
  
  runSystems(deltaTime: number) {
    // все системы обрабатываются одинаково
    for (const system of this.systems) {
      system.update(deltaTime, this, this.eventBus);
    }
  }
}

// Разные системы с разной реализацией
class PopulationSystem implements ISystem {
  update(deltaTime: number, ecs: ECSManager, eventBus: EventBus) {
    // реализация для населения
  }
}

class EconomySystem implements ISystem {
  update(deltaTime: number, ecs: ECSManager, eventBus: EventBus) {
    // реализация для экономики
  }
}
```

### Абстракция

Использование абстракций для скрытия деталей реализации и работы с концепциями высокого уровня.

#### В ядре

- **`GameCore`** — абстракция игрового ядра:
  - скрывает детали работы менеджеров;
  - предоставляет высокоуровневый API для работы с игрой.
- **`EventBus`** — абстракция событийной шины:
  - скрывает детали реализации публикации/подписки;
  - предоставляет высокоуровневый API для работы с событиями.
- **`ECSManager`** — абстракция ECS:
  - скрывает детали хранения entities, components, systems;
  - предоставляет высокоуровневый API для работы с ECS.

#### В модулях

- **Модули** — абстракция функциональности:
  - скрывают детали реализации систем и компонентов;
  - предоставляют высокоуровневый API для работы с модулем.
- **Системы** — абстракция логики обработки:
  - скрывают детали реализации обработки компонентов;
  - предоставляют высокоуровневый API через интерфейс `ISystem`.

#### Пример

```typescript
// ✅ Хорошо: абстракция через интерфейс
interface ISystem {
  id: string;
  priority: number;
  updateInterval: number;
  update(deltaTime: number, ecs: ECSManager, eventBus: EventBus): void;
}

// Реализация скрывает детали
class PopulationSystem implements ISystem {
  private populationData: Map<EntityId, PopulationComponent> = new Map();
  
  update(deltaTime: number, ecs: ECSManager, eventBus: EventBus) {
    // детали реализации скрыты
    const entities = ecs.getEntitiesWithComponent('Population');
    for (const entity of entities) {
      const component = ecs.getComponent<PopulationComponent>(entity, 'Population');
      // обработка компонента
    }
  }
}
```

## Применение принципов в архитектуре

### Ядро (Core)

- **Single Responsibility**: каждый менеджер отвечает за свою область (время, ECS, события, модули, команды).
- **Open/Closed**: ядро закрыто для модификации, открыто для расширения через модули и системы.
- **Liskov Substitution**: все системы, модули, команды взаимозаменяемы через интерфейсы.
- **Interface Segregation**: минимальные интерфейсы (`ISystem`, `IModule`, `ICommand`).
- **Dependency Inversion**: ядро зависит от абстракций (интерфейсов), а не от конкретных реализаций.

### Модули

- **Single Responsibility**: каждый модуль отвечает за свою область (здания, экономика, транспорт и т.д.).
- **Open/Closed**: модули закрыты для модификации, открыты для расширения через события и подписки.
- **Liskov Substitution**: все системы модулей взаимозаменяемы через интерфейс `ISystem`.
- **Interface Segregation**: модули используют только необходимые методы из интерфейсов.
- **Dependency Inversion**: модули зависят от абстракций (интерфейсов ядра), а не от конкретных реализаций.

### Подмодули и расширения

- **Single Responsibility**: каждый подмодуль отвечает за свою область.
- **Open/Closed**: подмодули закрыты для модификации, открыты для расширения через события.
- **Liskov Substitution**: все подмодули взаимозаменяемы через интерфейсы.
- **Interface Segregation**: подмодули используют только необходимые методы из интерфейсов.
- **Dependency Inversion**: подмодули зависят от абстракций (интерфейсов модулей), а не от конкретных реализаций.

## Рекомендации

1. **Предпочтение композиции над наследованием**: использовать интерфейсы и композицию вместо наследования.
2. **Минимальные интерфейсы**: создавать интерфейсы с минимальным набором методов.
3. **Зависимость от абстракций**: всегда зависеть от интерфейсов, а не от конкретных реализаций.
4. **Единственная ответственность**: каждый класс, модуль, система должны иметь только одну причину для изменения.
5. **Открытость для расширения**: проектировать систему так, чтобы можно было добавлять новую функциональность без изменения существующего кода.
