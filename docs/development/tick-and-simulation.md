# Тики и симуляция

Последнее обновление: 2025-11-23

Документ подробно описывает работу симуляции по тикам в Script City и её взаимодействие с другими подсистемами. Этот документ дополняет общий обзор в `architecture.md`.

## Цели системы тиков

- Обеспечить **предсказуемое** поведение симуляции.
- Отделить частоту **симуляции** от частоты **рендеринга**.
- Дать возможность:
  - паузы;
  - ускорения времени;
  - масштабирования до серверной симуляции (мультиплеер).

---

## Базовые понятия

- **Tick (тик)** — один шаг симуляции (обновление игрового состояния).
- **Tick rate** — количество тиков в секунду (например, 10 или 20).
- **Delta time (dt)** — длительность тика в секундах или миллисекундах.
- **GameState** — состояние мира на определённом тике.

Симуляция рассматривается как последовательность:

```
GameState_{n+1} = SimulateTick(GameState_n, Commands_n)
```

где `Commands_n` — список команд игрока и систем, применённых на шаге `n`.

---

## Жизненный цикл тика

Для однопользовательского режима (MVP) тик выглядит так:

### 1. Сбор ввода

- Считываются действия пользователя:
  - клики мышью по карте;
  - горячие клавиши;
  - действия UI (кнопки, переключатели, слайдеры).
- Формируются **команды**:
  - `BuildBuilding`;
  - `BulldozeArea`;
  - `ChangeTaxRate`;
  - `TogglePolicy`;
  - `SetSimulationSpeed` и т.п.
- Команды добавляются в очередь команд текущего тика.

### 2. Применение команд

- Ядро симуляции последовательно обрабатывает команды:
  - валидирует;
  - изменяет `GameState` (через системы и компоненты);
  - генерирует события (например, `ConstructionStarted`).
- Важно: команды не должны "обходить" системы и напрямую мутировать данные.

### 3. Фаза симуляции (системы ECS)

- Ядро запускает зарегистрированные системы **в фиксированном порядке**. Например:
  1. `PopulationSystem`
  2. `EconomySystem`
  3. `TransportSystem`
  4. `InfrastructureSystem`
- Каждая система:
  - читает только свои компоненты;
  - пишет только в свои компоненты;
  - при необходимости публикует события (Event Bus).
- Внутри одной фазы тика порядок вызова систем **детерминирован**.

### 4. Агрегация и пост-обработка

- Выполняются агрегирующие вычисления:
  - подсчёт бюджетных итогов за тик;
  - обновление счетчиков населения;
  - расчёт сводок по транспорту.
- Готовятся данные для UI:
  - высокоуровневые показатели;
  - статистика для панелей и графиков.

### 5. Фаза рендеринга

- На основе изменённых компонентов и событий:
  - обновляются спрайты объектов;
  - добавляются/удаляются спрайты;
  - применяются визуальные эффекты (например, анимации строительства).
- Если FPS рендера выше, чем tick rate, между тиками возможна интерполяция (в будущем).

## Режимы времени

### 1. Пауза

- Tick rate = 0 (тики не выполняются).
- Разрешены:
  - действия в UI;
  - изменение настроек;
  - подготовка команд (например, очередь строительства).
- Команды, влияющие на мир, либо:
  - копятся и применяются при выходе из паузы,
  - либо применяются сразу, но без продолжения процессов (например, строительство "замирает").

### 2. Нормальная скорость

- Tick rate, например, 10 тиков/сек.
- Каждый тик соответствует фиксированному шагу игрового времени (например, 1 "игровая минута").

### 3. Ускорение

- Логика та же, что и при нормальной скорости, но:
  - либо увеличивается tick rate (например, до 20–30 тиков/сек),
  - либо за один кадр может выполняться несколько тиков симуляции подряд.
- UI может обновляться реже, чем происходят тики (с сглаживанием отображения).

---

## Обработка лагов и пропущенных тиков

Если кадр занимает дольше, чем один тик, ядро:

1. Накапливает "долг" по времени.
2. Выполняет несколько тиков симуляции подряд, пока не догонит реальное время:
   - при необходимости без промежуточного рендера (skip-render ticks).
3. Ограничивает максимальное количество тиков подряд:
   - чтобы избежать "спирали смерти", когда симуляция не успевает обновляться.

## Разные частоты для разных подсистем

Не все системы обязаны обновляться в каждом тике:

- **Быстрые системы** (каждый тик):
  - транспорт (движение машин, пробки);
  - короткие процессы (анимации, короткие события).
- **Медленные системы** (раз в несколько тиков или по таймеру):
  - экономика (ежечасный/ежедневный пересчёт бюджета);
  - население (демография, миграция);
  - инфраструктура (ресурсы, обслуживание).

Реализация:

- у каждой системы есть свой "интервал обновления";
- ядро в каждом тике решает, какие системы нужно запускать.

## Взаимодействие с картой и чанками

Система тиков тесно связана с картой и чанками:

- **Чанки карты**:
  - симуляция может выполняться только для:
    - активных чанков (в зоне интереса камеры),
    - или для подмножества чанков в каждый тик (round-robin).
- **Неактивные чанки** (далеко от игрока):
  - могут обновляться реже;
  - часть процессов может быть агрегирована/упрощена.

Цель — не считать весь огромный мир на каждом тике, а распределять нагрузку.

## Команды и события

### Команды (Commands)

Команда — намерение изменить мир. Примеры:

- `BuildBuilding { position, buildingType }`
- `BulldozeArea { area }`
- `ChangeTaxRate { taxType, newRate }`
- `SetPolicy { policyId, enabled }`
- `SetSimulationSpeed { speedLevel }`

Команды:

- формируются UI;
- проверяются и применяются ядром;
- **одинаковы** для локальной и серверной симуляции.

### События (Events)

Событие — факт, который уже произошёл. Примеры:

- `ConstructionStarted`, `ConstructionCompleted`
- `TrafficJamStarted`, `TrafficJamResolved`
- `BudgetUpdated`, `PopulationChanged`

События:

- публикуются системами;
- используются другими модулями и UI для реакции;
- служат основой для логов, аналитики, анимаций.

## Поддержка мультиплеера (концептуально)

Модель тиков и команд изначально проектируется так, чтобы её можно было перенести на сервер.

### Локальный режим (MVP)

- `GameState` и тики живут **целиком в браузере**.
- Команды:
  - формируются UI;
  - сразу применяются к локальному состоянию.
- Сохранения:
  - сериализация `GameState` (по чанкам или целиком);
  - хранение в IndexedDB/файлах.

### Серверный режим (Post-MVP)

- Авторитетный `GameState` живёт **на сервере**.
- Клиент:
  - формирует команды и отправляет на сервер (через WebSocket/Socket.io);
  - получает:
    - снапшоты состояния (целого мира или чанков),
    - или дельты (патчи) между снапшотами.
- Сервер:
  - применяет команды и крутит тики так же, как локальное ядро;
  - рассылает результаты клиентам.

Важно:

- форматы `GameState`, `Command` и `Event` максимально переиспользуются между локальным и серверным режимом;
- локальный режим рассматривается как "сервер в одном процессе".

## Тестирование симуляции

Рекомендуется:

- покрывать модульными тестами:
  - отдельные системы ECS (экономика, население, транспорт);
  - обработчики команд (валидность, эффекты).
- писать сценарные тесты:
  - несколько тиков подряд;
  - проверка ожидаемого состояния `GameState`;
  - проверка ожидаемых событий.

Это особенно важно для сохранения детерминированности симуляции при развитии проекта.
